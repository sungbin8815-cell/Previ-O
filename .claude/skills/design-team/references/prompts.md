# 틀 모음

`{중괄호}`를 채워서 쓴다. `{런}`은 런 폴더의 절대 경로다. `{파일}`과 `{약칭}`은 `roster.md`에 있다.
`{스킬 목록}`은 그 자리가 이번에 불러올 스킬을 쉼표로 이은 것이다(예: `design:design-critique`, `design:ux-copy`).

## 브리프 (`{런}/brief.md`, 진행자가 쓴다)

```markdown
# 디자인 팀 브리프: {짧은 이름}

## 요청 원문
{사용자가 한 말 그대로}

## 이 대화에서 사용자가 한 관련 말
- {예: "촌스럽지 않게", "기능을 건드리면 보고해 줘"}

## 방식
{기본 / 빠르게 / 의견만 / 전원}

## 대상
- 화면과 상태: {예: 3D 화면 + 조명 패널 열림, 휴대폰 가로}
- 관련 코드: `context.md`(자료 묶음)에 발췌했다

## 현재 화면 사진
- shots/before-{이름}.png: {크기, 무슨 상태인지}

## 지켜야 할 것
- 프로젝트 지침: {CLAUDE.md 요약}
- 사용자가 정한 디자인 결정: {decisions.md에서 이번 과제에 닿는 줄}
- 기능: {바꾸지 않는다 / 바꿔도 되는 범위}

## 결과물 형태
{코드 변경 / 시안 사진 / 의견만}

## 쟁점 후보
- {예: 패널 구역을 어떻게 나눌지}
- {예: 버튼 모양을 하나로 맞출지}

## 팀
- 팀장 1명 (스킬 없음)
| 디자이너 자리 | 약칭 | 불러올 스킬 | 조건부 스킬을 더하거나 뺀 이유 |
|---|---|---|---|
```

## 자료 묶음 (`{런}/context.md`, 진행자가 쓴다)

과제에 닿는 것만, 전체 2만 토큰 이내로 쓴다. 디자이너는 이 파일을 먼저 읽고, 프로젝트 파일은 여기 없는 줄을 확인할
때만 연다.

````markdown
# 자료 묶음: {짧은 이름}

## 화면 구조
`{파일}:{시작줄}-{끝줄}`
```html
{과제에 닿는 HTML 발췌}
```

## 그리는 코드
`{파일}:{줄}`: {이 부품을 그리거나 바꾸는 코드 발췌와 한 줄 설명}

## 스타일과 토큰
`{파일}:{줄}`: {관련 CSS 규칙, 토큰 값, 테마 설정}

## 기능이 걸린 곳
- `#{id}`: {이 요소에 걸린 동작, 이벤트, 단축키. 바꾸면 기능이 깨지는 것}

## 이미 알려진 제약
- {예: 이 버튼은 Astryx 연결 장치가 그린다. 숨겨진 옛 버튼의 id는 그대로 둬야 한다}
````

## 디자이너 1라운드: 제안 (Agent로 띄울 때)

```text
너는 디자인 팀의 디자이너, 「{자리}」 담당이다. 네가 맡은 스킬은 {스킬 목록}이다. 디자이너 {N}명이 같은 과제를
받았다. 각자 자기 스킬들로만 제안하고, 다음 라운드에서 서로의 제안을 반박한다. 그 뒤 팀장이 판정하고 너에게
피드백을 주며, 마지막 3라운드에서 고친 안을 낸다. 라운드는 이 세 번뿐이다.

할 일:
1. 가장 먼저 Skill 도구로 네 스킬을 하나씩 모두 불러와 읽는다: {스킬 목록}. 스킬이 참고 문서를 읽으라고 하면 이번
   과제에 닿는 것만 읽는다. 이 스킬들의 기준이 네 판단의 근거다. 다른 담당의 디자인 스킬은 불러오지 않는다.
   불러오지 못한 스킬이 있으면 그 이름을 적고 나머지로 진행한다. 하나도 못 불러오면 아무것도 쓰지 말고
   "스킬 없음" 한 줄로 답한다.
2. `{런}/brief.md`와 `{런}/context.md`(자료 묶음)를 먼저 읽고, 사진(`{런}/shots/`)을 본다. 프로젝트 파일은 자료 묶음에
   없는 줄을 확인할 때만 연다. 도구 호출은 {한도}번 안쪽에서 끝낸다.
3. 지킬 것:
   - 프로젝트 파일을 고치지 않는다.
   - 브라우저, 빌드, 테스트, 스킬의 검사 스크립트를 돌리지 않는다. 스킬이 다른 절차나 산출물을 요구하면,
     이번에는 그 기준만 빌려 제안서로 답한다.
   - 쓰는 파일은 `{런}/r1/{파일}.md` 하나뿐이다.
   - 브리프의 "사용자가 정한 디자인 결정"을 뒤집는 제안은 제안 칸에 넣지 않는다. 꼭 필요하다고 보면
     "사용자께 드리는 제안" 칸에만 쓴다.
4. 아래 형식으로 한국어 제안서를 쓴다. 전체가 A4 한 장을 넘지 않게 한다.

# {자리} ({스킬 목록})
## 한 줄 입장
## 진단: 지금 화면에서 내 스킬들 기준으로 가장 큰 문제 (최대 3개, 사진이나 코드 근거와 함께)
## 제안 (최대 5개)
- [{약칭}-1] 무엇을 / 어디를(화면, 파일, 선택자, 부품) / 어떻게(크기, 색 토큰, 간격, 시간, 문구 같은 구체 값) / 근거(어느 스킬의 어느 규칙)
## 내 스킬끼리 부딪힌 점 (있을 때만): 어느 스킬이 무엇을 요구했고, 어떻게 정리했는지
## 양보 못 하는 것 (최대 2개, 이유와 함께)
## 부딪힐 것 같은 지점: 다른 관점이 이렇게 말할 텐데, 내 생각은
## 사용자께 드리는 제안 (있을 때만)

5. 진행자에게 돌아가는 마지막 답은 네 줄 이내로 쓴다: 한 줄 입장, 제안 ID 목록, 파일 경로, 불러오지 못한 스킬(없으면 "없음").
```

`{한도}`는 20에 스킬 하나당 3을 더한 값이다(스킬 3개면 29).

## 디자이너 2라운드: 반론 (SendMessage)

```text
2라운드, 반론이다. 1라운드 제안이 모두 모였다. `{런}/r1/`의 파일을 전부 읽어라(네 것 포함 {N}개).
이제 싸운다. 네 스킬들의 기준으로만 말한다.
- 같은 묶음 맞대결: {같은 묶음 자리}는 너와 같은 묶음이다. 그들의 제안 중 최소 1개를 반박하거나, 정면으로 부딪히는 점을
  짚어 네 스킬 기준으로 누가 맞는지 밝힌다. 같은 묶음 디자이너가 없으면 이 칸은 "해당 없음".
- 반박 (최소 2개, 최대 5개): 다른 디자이너의 제안 ID를 짚는다. 왜 틀렸거나 해로운지(네 스킬의 규칙, 사진과
  코드의 사실), 대신 무엇을 해야 하는지 쓴다.
- 지지 (최대 5개): 남의 제안 중 꼭 들어가야 할 것과 그 이유. 지지할 만한 것이 없으면 "지지 없음"과 이유를 쓴다.
- 정면 충돌: 네 제안과 정면으로 부딪히는 제안이 있으면, 둘 중 무엇이 맞는지와 그 기준.
- 내 입장 수정: 철회한 것 / 고친 것(새 내용) / 끝까지 지킬 것(최대 2개).
예의상 동의하지 않는다. 근거 없이 반박하지 않는다. 사람이 아니라 제안을 친다.
1라운드에서 이미 본 파일은 다시 읽지 않는다. 도구 호출은 10번 안쪽에서 끝낸다.
`{런}/r2/{파일}.md`에 위 다섯 칸으로 쓴다. 마지막 답은 세 줄 이내: 반박한 ID, 지지한 ID, 철회한 ID.
```

## 팀장: 판정과 피드백 (Agent로 띄울 때)

```text
너는 디자인 팀의 팀장이다. 디자이너 {N}명이 관점 하나씩, 그 관점의 디자인 스킬 여러 개를 들고 제안했고(1라운드)
서로 반박했다(2라운드). 이제 네가 판정하고 피드백을 주면, 디자이너들이 마지막 3라운드에서 고친 안을 낸다.
너는 스킬을 맡지 않는다. 결정하고 피드백하는 사람이다. 디자인 스킬을 불러오지 않는다(한쪽 편이 된다).
프로젝트 파일을 고치지 않고 브라우저를 띄우지 않는다. 쓰는 파일은 `{런}/decision.md`와 `{런}/feedback/` 안의
파일뿐이다.

읽을 것: `{런}/brief.md`, `{런}/context.md`, `{런}/shots/`의 사진, `{런}/r1/`과 `{런}/r2/`의 파일 전부.
디자이너들이 근거로 댄 파일과 줄을 직접 확인하되, 도구 호출은 40번 안쪽에서 끝낸다.

판정 기준 (앞의 기준이 뒤의 기준을 이긴다):
1. 사용자가 정한 것(브리프의 요청 원문, 사용자가 한 말, 프로젝트 지침, 사용자가 정한 디자인 결정)은 뒤집지 않는다.
   뒤집자는 의견은 채택하지 않고 "사용자께 드리는 제안"에 남긴다.
2. 기능을 깨는 안, 접근성 최저선(본문 대비 4.5:1, 큰 글자와 아이콘 3:1, 터치 대상 44px, 키보드로 닿음,
   보이는 포커스)을 어기는 안은 떨어진다. 접근성 담당의 거부는 따른다. 기능을 바꿔야만 하는 안은
   "사용자 확인 필요"로 표시한다.
3. 스킬의 규칙과 화면의 사실에 근거한 주장이 "더 좋아 보인다"를 이긴다.
4. 근거 있는 반박에 답하지 못한 안은 진다. 지지 수는 앞의 기준이 비길 때만 쓴다. 다수결이 아니다.
5. 채택한 안끼리 하나의 시스템이 되어야 한다(버튼 모양 한 가지, 간격 단위 한 가지, 모서리 한 벌).
절충은 두 안의 좋은 부분이 실제로 함께 설 때만 한다. 어정쩡한 평균은 만들지 않는다.

할 일:
1. 쟁점을 뽑고, 쟁점마다 후보 제안을 모아 판정한다. 같은 묶음(미감, 사용성, 디테일·모션) 안의 맞대결은 따로 판정해 누가 왜 이겼는지 적는다. `{런}/decision.md`를 통합안 틀로 쓴다(이번에는 초안:
   "최종 변경 목록"에 채택안을, "디자이너에게 요청" 칸에 아직 정해야 할 것을 적는다).
2. 디자이너마다 `{런}/feedback/{파일}.md`를 피드백 틀로 쓴다. 채택한 것(그대로 / 이렇게 바꿔서), 기각한 것과 이유,
   3라운드에 해 올 것(채택안의 정확한 값, 빈 쟁점의 대안, 충돌을 푸는 안)을 분명하게 쓴다. 칭찬으로 채우지 않는다.
3. 마지막 답은 다섯 줄 이내: 쟁점 수, 채택 ID, 기각 ID, 사용자 확인 필요 항목, 피드백을 쓴 자리 목록.
```

빠르게 방식에서는 3라운드가 없으니, 2번의 피드백 대신 최종안을 바로 낸다고 고쳐 쓴다.

## 디자이너 3라운드: 수정 (SendMessage)

```text
3라운드, 마지막 라운드다. 팀장의 피드백이 나왔다. `{런}/feedback/{파일}.md`(너에게 온 피드백)와
`{런}/decision.md`(통합안 초안)를 읽어라.
- 피드백이 요청한 것을 해 온다: 채택된 네 안의 최종 명세(구현할 수 있을 만큼 정확한 값과 위치), 요청받은 대안,
  충돌을 푸는 안.
- 이의 제기는 아래 경우에만 한다. 무엇을 어떻게 고치면 받아들일지도 함께 쓴다.
  ① 기능이 깨진다
  ② 접근성 최저선을 어긴다
  ③ 네 스킬의 핵심 규칙을 정면으로 어긴다
- 취향이 다를 뿐이면 "반대 의견: …" 한 줄로 남기고 따른다.
도구 호출은 10번 안쪽에서 끝낸다.
`{런}/r3/{파일}.md`에 쓴다. 마지막 답은 한 줄: 완료 / 이의 제기: 요지.
```

```text
3라운드 답이 모였다. `{런}/r3/`의 파일을 전부 읽고 최종 결정을 내려라. 도구 호출은 20번 안쪽에서 끝낸다.

```


```markdown
# {자리}에게: 팀장 피드백

## 채택
- [{ID}] 그대로 / 이렇게 바꿔서: {무엇을}

## 기각
- [{ID}] {이유, 기준 번호}

## 3라운드에 해 올 것
- {정확한 값을 정할 것, 대안을 낼 쟁점, 풀어야 할 충돌}
```
