# 디자인 팀

디자인 요청 하나를 팀 프로젝트처럼 처리한다. 사람은 세 종류다.

| 누구 | 몇 명 | 하는 일 |
|---|---|---|
| **디자이너** | n명 (디자인 스킬 하나에 한 명) | 자기 스킬 기준으로만 제안하고, 서로 반박하고, 팀장의 피드백에 맞춰 고친다 |
| **팀장** | 1명 (서브에이전트) | 스킬 자리를 맡지 않는다. 쟁점마다 판정하고, 디자이너마다 피드백을 주고, 최종 결정을 내리고, 결과를 검토한다 |
| **진행자** | 메인 대화의 Claude (너) | 브리프를 쓰고, 화면을 찍고, 팀을 띄우고, 라운드를 넘기고, 최종안을 구현하고, 사용자에게 보고한다. **디자인을 판정하지 않는다** |

진행자는 팀장의 결정에 디자인 의견을 보태지 않는다. 다만 결정이 사용자가 정한 것이나 기능을 어기면 이유를
붙여 팀장에게 돌려보낸다. 기능을 바꿔야만 하는 결정이면 구현하기 전에 사용자에게 묻는다.

## 0. 흐름

1. **브리프** (진행자): 과제, 현재 화면 사진, 지켜야 할 것
2. **1라운드 제안** (디자이너 전원, 동시): 자기 스킬로만 제안
3. **2라운드 반론** (디자이너 전원): 서로의 제안을 ID로 짚어 반박하고 지지한다. 싸움이다
4. **판정과 피드백** (팀장): 쟁점마다 판정한 통합안 초안, 디자이너별 피드백
5. **3라운드 수정** (디자이너 전원): 피드백에 답한다. 채택된 안의 최종 명세, 요청받은 대안, 이의 제기
6. **최종 결정** (팀장): 이의를 처리하고 구현할 수 있을 만큼 구체적인 최종안을 낸다
7. **구현** (진행자 혼자. 여러 명이 한 파일을 동시에 고치지 않게)
8. **검토** (팀장과 거부권자 두 명): 결과 사진을 보고 고칠 것을 낸다
9. **보고** (진행자): 판정표, 팀원별로 가져온 것, 싸움의 요지, 기각된 의견, 기능을 건드린 점

## 1. 방식

| 방식 | 언제 | 단계 |
|---|---|---|
| 기본 | 디자인 요청 전부 | 1~9, 참여 조건에 맞는 디자이너 전원 |
| 빠르게 | 사용자가 "빠르게"라고 할 때, 또는 값 하나·문구 하나 수준의 작은 수정 | 디자이너 6명(`references/roster.md`의 빠르게 명단). 1, 2, 3, 4(팀장이 바로 최종 결정), 7, 8(팀장만), 9 |
| 의견만 | "의견만", "토론만", "시안만" | 1~6. 구현 없이 최종안과 판정표만 보고 |
| 전원 | "전원" | 기본과 같되, 참여 조건에 안 맞는 디자이너까지 모두 앉힌다 |

작은 수정이라 빠르게로 바꿨으면, 시작할 때 그렇다고 한 줄로 알리고 "전체 토론을 원하시면 말씀해 주세요"를 붙인다.

## 2. 팀 꾸리기

- 명단은 `references/roster.md`다. 이 세션의 스킬 목록과 대조해서, 목록에 없는 스킬의 자리는 비우고, 명단에 없는
  새 디자인 스킬이 보이면 자리를 하나 만든다(명단 파일에도 적는다).
- 자리마다 참여 조건을 보고 이번 과제에 닿는 디자이너만 앉힌다. 빠진 자리는 보고에 한 줄씩 이유를 쓴다.
- 팀장은 늘 한 명 앉는다. 디자인 스킬을 불러오지 않는다. 한 스킬의 편이 되지 않기 위해서다.
- **거부권**: 접근성 두 자리(`audit-suite:audit-as-a11y-eng`, `design:accessibility-review`)는 거부권이 있다. 기능을
  막거나 접근성 최저선(본문 대비 4.5:1, 큰 글자와 아이콘 3:1, 터치 대상 44px, 키보드로 닿음, 보이는 포커스)을 어기는
  안은 팀장도 채택할 수 없다.
- 시작할 때 사용자에게 한 번 알린다: 방식, 디자이너 수와 자리 이름, 팀장, 라운드 수, 대략의 규모(아래 "비용").
- **비용**: 시험 회차에서 디자이너 한 명이 1라운드에 약 25만 토큰과 15분을 썼다(도구 54번). 라운드마다 도구 호출
  한도를 두었지만, 기본 방식으로 십여 명이 앉으면 한 번에 수백만 토큰이 든다. 팀원은 동시에 돌아서 라운드마다
  십몇 분씩 걸린다. 브리프에 파일과 줄 범위를 정확히 적어 팀원이 헤매지 않게 하는 것이 가장 큰 절약이다.

## 3. 런 폴더와 브리프

- 런 폴더: 세션 스크래치패드 아래 `design-team/<YYYYMMDD-HHMM>-<짧은-이름>/`. 스크래치패드가 없으면 프로젝트의
  `.design-team/` 아래에 만든다(`.gitignore`에 있어 커밋되지 않는다).
- 하위: `brief.md`, `team.md`, `shots/`, `r1/`, `r2/`, `feedback/`, `r3/`, `decision.md`, `review/`.
- 진행자가 먼저 현재 화면을 찍어 `shots/before-*.png`에 둔다. 과제에 맞게 넓은 화면, 휴대폰 가로, 휴대폰 세로,
  해당 패널이 열린 상태 등. 팀원은 브라우저를 띄우지 않으니 필요한 화면은 진행자가 다 찍어 둔다.
- `brief.md`는 `references/prompts.md`의 브리프 틀로 쓴다. 꼭 넣을 것: 요청 원문, 이 대화에서 사용자가 한 관련 말,
  대상 화면과 파일·선택자, 사진 목록, 프로젝트 지침 요약(`CLAUDE.md`), 사용자가 이미 정한 디자인 결정
  (`references/decisions.md`에서 이번 과제에 닿는 것), 결과물 형태, 쟁점 후보, 팀 명단과 제안 ID 약칭.

## 4. 라운드 진행 규칙

- 디자이너는 **한 메시지에 Agent 호출을 모두 넣어** 동시에 띄운다(`subagent_type: "general-purpose"`, 설명은
  `디자인팀 <자리>`). 한 번에 띄울 수 있는 수를 넘으면 나눠 띄운다. 팀장은 4단계에서 띄운다(설명은 `디자인팀 팀장`).
- 프롬프트는 `references/prompts.md`의 틀을 그대로 채운다. 디자이너는 시작하자마자 Skill 도구로 자기 스킬을
  불러오고, 그 스킬 기준으로만 말한다.
- 팀원은 프로젝트 파일을 고치지 않고, 브라우저·빌드·테스트를 돌리지 않는다. 쓰는 파일은 런 폴더 안의 자기 파일뿐이다.
- 띄운 뒤 `team.md`에 자리, 스킬, 에이전트 ID를 적는다. 대화가 요약돼도 이 파일로 이어 간다.
- **2라운드부터는 새로 띄우지 않고 SendMessage로 같은 팀원에게 보낸다**(`to`에 그 팀원의 에이전트 ID).
  그래야 디자이너는 불러 둔 스킬과 앞 라운드의 생각을, 팀장은 판정의 맥락을 그대로 들고 간다. 이어 보낼 수
  없으면 새 Agent를 띄우되, 디자이너는 스킬부터 다시 불러오게 하고, 그 자리의 이전 파일 경로를 준다.
- 한 라운드의 팀원이 모두 끝났다는 알림이 오기 전에는 다음 단계로 가지 않는다. 결과를 짐작해서 쓰지 않는다.
  기다리는 동안 사용자에게 진행 상황을 한 줄로 알린다.
- 디자이너가 실패하거나 "스킬 없음"이라고 답하면 한 번 다시 띄운다. 또 안 되면 그 자리는 빠진 것으로 보고한다.
- 사용자가 중간에 말을 보태면 그 말을 팀장에게 바로 전한다. 사용자의 말은 어떤 판정보다 앞선다.

## 5. 팀장의 판정 기준

팀장 프롬프트에 그대로 넣는다. 앞의 기준이 뒤의 기준을 이긴다.

1. **사용자가 정한 것**: 이 대화에서 사용자가 말한 것, `CLAUDE.md`, `references/decisions.md`. 팀이 뒤집을 수 없다.
   뒤집자는 의견은 채택하지 않고 "사용자께 드리는 제안"에 남긴다.
2. **기능과 접근성 최저선**: 기능을 깨는 안, 거부권 기준을 어기는 안은 떨어진다. 기능을 바꿔야만 하는 안은
   "사용자 확인 필요"로 표시한다.
3. **근거의 질**: 자기 스킬의 규칙과 이 화면의 사실(사진, 코드)에 근거한 주장이 "더 좋아 보인다"를 이긴다.
4. **반론을 견뎠는가**: 근거 있는 반박을 받고 답하지 못한 안은 진다. 여러 자리의 지지를 받은 안이 이긴다.
   지지 수는 앞의 기준이 비길 때만 쓴다. 다수결이 아니다.
5. **하나의 시스템**: 채택한 안끼리 서로 맞아야 한다(버튼 모양 한 가지, 간격 단위 한 가지, 모서리 크기 한 벌).
   충돌하면 더 넓고 일관되게 적용되는 쪽을 고른다.

절충은 두 안의 좋은 부분이 실제로 함께 설 때만 한다. 어정쩡한 평균은 만들지 않는다. 판정마다 이유와 기준 번호를
남긴다. 피드백은 디자이너마다 따로, 무엇을 왜 채택·기각했는지와 다음에 무엇을 해 오라는지 분명하게 쓴다.

## 6. 구현과 검토

- **구현**: 진행자가 `decision.md`의 최종 변경 목록대로, 프로젝트 지침에 따라 고친다. 이 저장소에서는
  `CLAUDE.md`의 Astryx 연결 장치 규칙을 따르고, `ui/`를 고쳤으면 다시 빌드하고, 기존 테스트를 돌린다.
  최종안에 없는 것을 슬쩍 더하지 않는다. 구현하다 최종안이 맞지 않으면, 팀장에게 SendMessage로 알려 결정을 받는다.
- **기능 보고**: 동작, 단축키, 저장 형식, 요소 구조(id·class·data 속성), 성능을 건드렸으면 무엇을 왜 바꿨는지
  모아 둔다. 보고에 반드시 넣는다.
- **검토**: 결과 사진 `shots/after-*.png`를 찍고, 팀장과 거부권자 두 명에게 SendMessage로 검토를 맡긴다. 전원
  검토는 사용자가 원할 때만 한다. 팀장이 고칠 것 목록을 확정하면 진행자가 고치고 다시 찍는다(최대 2번).

## 7. 보고 (사용자에게, 한국어)

1. 한 줄 결론
2. 팀: 방식, 디자이너 자리와 스킬, 빠진 자리와 이유, 팀장
3. 판정표: 쟁점마다 누가 무엇을 주장했고, 누가 반대했고, 팀장이 무엇을 골랐고, 왜 골랐는지
4. 디자이너별로 가져온 것(크레딧)과, 가장 크게 부딪힌 싸움 한두 개
5. 팀장의 피드백으로 바뀐 것
6. 기각된 큰 의견, 사용자 결정을 바꾸자는 제안(채택하지 않음, 판단은 사용자 몫)
7. 남은 반대 의견
8. 구현: 바뀐 것, 기능을 건드린 점, 테스트 결과, 전후 사진(SendUserFile)
9. 커밋과 푸시 여부

## 8. 하지 말 것

- 팀원 결과를 기다리지 않고 짐작으로 넘어가기
- 진행자가 디자인을 판정하거나, 디자인 스킬을 불러와 한쪽 편들기
- 팀장이 디자인 스킬을 불러오기
- 팀원에게 프로젝트 파일 수정이나 브라우저 실행을 맡기기
- 사용자가 정한 것을 팀 다수결이나 팀장 판정으로 뒤집기
- 판정 이유 없이 "종합하면"으로 뭉개기
